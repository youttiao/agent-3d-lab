## A. TRELLIS and TRELLIS.2

### A.1 TRELLIS v1 (`microsoft/TRELLIS`)

```
Repo            microsoft/TRELLIS   · 14,377 stars · pushed 2026-10-27 (last main commit 2026-10-27)
License         MIT (code + weights, microsoft/TRELLIS-image-large / -text-{base,large,xlarge} on HF)
Paper           arXiv 2412.01506 (CVPR'25 Spotlight)
Conditioning    TEXT ✅ and IMAGE ✅  — TRELLIS-text-{base,large,xlarge} released 2025-03-25
Output          Mesh + Gaussians + Radiance Fields, all from one SLAT latent
Texture         RGB albedo atlas only. NO metallic/roughness maps, NO normal map, NO opacity
Faces           raw mesh ≈ 10^5 (256³ FlexiCubes grid); to_glb default simplify=0.95 → ~5% retained
Topology        Single connected mesh after post-process; interior shells stripped by visibility mincut
Watertight      NO GUARANTEE, but the shipped GLB path DOES run hole-filling
```

**Text-to-3D: yes.** README: *"It takes in text or image prompts."* Text checkpoints `TRELLIS-text-base|large|xlarge` exist, with `ss_flow_txt_dit_*` / `slat_flow_txt_dit_*` configs. The authors explicitly downgrade it: *"It is always recommended to do text to 3D generation by first generating images using text-to-image models and then using TRELLIS-image models for 3D generation. Text-conditioned models are less creative and detailed due to data limitations."*

**`outputs['mesh']` is a list — confirmed from source.** `trellis/models/structured_latent_vae/decoder_mesh.py`:

```python
def to_representation(self, x: sp.SparseTensor) -> List[MeshExtractResult]:
    ret = []
    for i in range(x.shape[0]):
        mesh = self.mesh_extractor(x[i], training=self.training)
        ret.append(mesh)
    return ret
```

So the list length = the SLAT batch dimension = `num_samples` (default **1**). Practically: one mesh per sample, and the README's `outputs['mesh'][0]` is just "the only sample". It is *not* "a list of components of one object" — a single asset is one mesh.

**Mesh → GLB pipeline** (`trellis/utils/postprocessing_utils.py`, verified line-by-line):
1. `postprocess_mesh()` → quadric-edge-collapse decimation via pyvista (ratio = `simplify`, default **0.95** = 95 % of triangles *removed*).
2. `_fill_holes()` → rasterizes the mesh from **500–1000 Hammersley views** at 1024², counts per-face visibility, computes connected components, and runs an **igraph mincut** to delete interior faces connected to the outer shell through a small hole; then `pymeshfix` `fill_small_boundaries(nbe=max_hole_nbe, refine=True)`.
3. `parametrize_mesh()` → **xatlas** UV unwrap.
4. `bake_texture()` → RGB atlas baked from 100 multiview renders of the appearance rep, `cv2.inpaint` for empty texels.
5. Material is `trimesh.visual.material.PBRMaterial(roughnessFactor=1.0, baseColorTexture=texture)` — **a placeholder roughness, no ORM texture, no metallic**. So TRELLIS v1's "PBR" is albedo + constant roughness.

**Known geometry complaints.** GitHub issue [#59 "3D printing"](https://github.com/microsoft/TRELLIS/issues/59) (2024-12-12, still open) is the canonical user report: *"The support for 3D printing is very bad… The problem is that a lot of the faces have holes."* No maintainer reply.

### B.2 Shape topology — the "shell" question

The 2.x shape path is **SDF → marching cubes**. `hy3dgen/shapegen/models/autoencoders/surface_extractors.py`:

```python
class DMCSurfaceExtractor(SurfaceExtractor):
    def run(self, grid_logit, *, octree_resolution, **kwargs):
        from diso import DiffDMC
        sdf = -grid_logit / octree_resolution
        verts, faces = self.dmc(sdf, deform=None, return_quads=False, normalize=True)
```

`MCSurfaceExtractor` (the default) is `skimage.measure.marching_cubes(..., method="lewiner")`.

**There is no watertight/manifold guarantee anywhere** — not in README, not in `docs/source/modelzoo.md`, not in the API docs. The only `watertight` strings in the repo refer to *training data* filenames (`{uid}_watertight.obj`).

**There is no shipped mesh-repair step for shape output.** `postprocessors.py` contains only `FaceReducer` (pymeshlab quadric edge collapse, `preserveboundary=True` — which *preserves* open boundaries rather than closing them), `FloaterRemover` (`nbfaceratio=0.005`), `DegenerateFaceRemover`, `MeshSimplifier` (shells out to an external `mesh_simplifier.bin` that is **missing from the repo tree**), and `mesh_normalize`. No hole filling, no `trimesh.repair`, no non-manifold edge repair. And in Hunyuan3D-2's `api_server.py` these run **only when texturing is requested**; the shape-only examples (`minimal_demo.py`, `examples/shape_gen.py`) do literally `mesh.export('demo.glb')` with zero post-processing.

**The watertight machinery that does exist is training-data preprocessing:** `hy3dshape/tools/watertight/watertight_and_sample.py` — an *offset shell* construction (`igl.signed_distance` + `igl.marching_cubes(epsilon - np.abs(sdf), …)`) that deliberately thickens the object by ~2ε so the SDF is well-defined. `hy3dshape/tools/evaluation/is_watertight.py` is the only shipped watertight test (`igl.boundary_loop` + `igl.is_edge_manifold` + `igl.is_vertex_manifold`). So Hunyuan3D's watertightness is an **emergent property of SDF extraction over watertight training data**, not a contract — which is exactly why hole reports appear.

**Output pipeline (from `docs/pipeline.md`, quoted):**

> **Stage 4: VAE decode and mesh extraction** … The decoder predicts per-corner signed distances and vertex deformations. **FlexiCubes extracts a triangle mesh, and ear clipping fills remaining holes.** Between passes, direct surface voxelization of the extracted mesh produces the next sparse support.
>
> **Stage 5: postprocessing** … 1. **Disconnected components with fewer than 0.5% of all faces are removed; the largest component is always retained.** 2. `pyfqmr` simplifies toward **1,000,000 faces at 512³ or 1024³, and 2,000,000 at 1536³**. … 3. The mean vertex position is subtracted, then vertices are scaled so the maximum radius is one. **Input world-space position and absolute scale are not preserved.**
>
> **Output contains geometry only, without materials, textures, or vertex colors.**

**So: effectively a single connected component (largest retained, sub-0.5%-of-faces debris dropped), hole-filled, 1–2 M triangles, normalized to unit radius.** Absolute scale is destroyed — you must re-scale before printing.

**Slicing Success Rate (SSR) methodology — verbatim:**

> We evaluate slicing success for each generated mesh using the **PrusaSlicer-family CLI in Bambu Studio**. - **Novelty = Spatial Sparse Attention (SSA)**: *"SSA allows the model to effectively process large token sets within sparse volumes … achieving a 3.9× speedup in the forward pass and a 9.6× speedup in the backward pass."* Headline claim: *"training at 1024³ resolution with just 8 GPUs"*, where *"a task typically requiring at least 32 GPUs for volumetric representations at 256³ resolution."* Three stages: dense-64 DiT → sparse-512 DiT (+ UNet3D refiner) → sparse-1024 DiT.
- **Image-to-3D only.** `models/conditioner.py` has no text conditioner; the pipeline takes a single image path.
- **Output = mesh only. There is no texture or PBR release** — `pipeline.py` ends with `outputs = {"mesh": mesh}`, and grepping the whole `direct3d_s2/` tree for `texture|albedo|pbr|metallic|roughness|material` returns **zero hits**. This is the biggest output-side regression vs. TRELLIS.
- **Topology handling:** `remove_interior=True` by default runs a UNet3D refiner at `mc_threshold*2.0` to strip enclosed interior surfaces — making the output a single outer shell rather than a multi-shell blob, but it is a *learned refiner*, not a topological guarantee. `remesh=True` calls `utils/fill_hole.py::postprocess_mesh` → mincut-based inner-side face removal (`max_hole_size=0.04`) + `mesh.fill_small_boundaries(nbe=32, refine=True)` + simplification — but **`remesh` defaults to `False`**. No `is_watertight` assertion in the repo.
- SOTA claim: *"surpasses state-of-the-art methods in generation quality and efficiency."* v1.2 was announced "being prepared" on 2025-06-03 and **there is no v1.2 code in the repo** (HF unverifiable).
- **Direct3D-V3 (the 2026 successor)** removes the VAE bottleneck: *"we introduce an **implicit manifold regularization** over neighboring voxels to **suppress non-watertight surfaces**, and convert predicted SDF grids into meshes via Marching Cubes so that rendered normal losses can supervise the model directly from its predicted SDF."* Released: inference code + weights (`wushuang98/Direct3D-V3`). **Not released: coarse-mesh generation models, the latent-free texture generation model, training code.**
- Hi3D's study measures **Direct3D-S2 at 1024³ = 80 % SSR** — middling, consistent with its unfilled holes.

### G.7 SUPRA-Tex (`Supra-3D/SUPRA-Tex`)

```
1,044 stars · pushed 2026-10-29 · MIT (with a Qwen non-commercial caveat) · arXiv 2610.22352 (2026-10-15)
Huawei Inc. + SJTU + HUST
```

**It is a texture-completion module, not a geometry model.** README: *"SUPRA-Tex generates textured 3D assets from a single image… It predicts PBR materials in the reference view, encodes them as surface-aligned 3D observations, and completes unseen regions with an Interleaved Flow Transformer. The output is a **relightable GLB with base color, metallic, and roughness textures**."*

- **Geometry frontend = Pixal3D** (vendored snapshot in `deployment/runtime/geometry/`); the repo also ships `TRELLIS2-MIT.txt` and `TENCENT-MIT.txt` — *"Our implementation builds on TRELLIS.2 and Pixal3D."* Camera estimation via MoGe-2; foreground via RMBG-2 or BiRefNet; material adapter built on Qwen-Image.
- **Output:** `outputs/<name>.glb` with **three** maps (base color, metallic, roughness) — full PBR. `--decimation-target` default **500,000** exported faces. Also supports texturing a pre-existing mesh (`texturing.py --input-dir …`) and a dual-view mode (front image + generated back view).
- **Weights are public and ungated** (`huggingface.co/supra3d/supra-tex`) — but **DINOv3** and **RMBG-2** require access approval (BiRefNet is the ungated substitute).
- **License nuance:** *"Original SUPRA-Tex source code and the 3D completion weights are released under the MIT License… **Built with Qwen:** the material adapter uses the **Qwen Research License for non-commercial research and evaluation**."* → the completion model is MIT; the material adapter is not commercially usable.
- Tested on a 24 GB RTX 3090 with CPU offload.

## I. Cross-cutting findings

### I.1 The 2026 split: two camps, and it is a representation decision, not a modelling one

The single sharpest sentence in the whole 2026 corpus is Hi3D 3.0's critique of the TRELLIS.2 family (arXiv 2610.11685):

> while **O-Voxel/FaithC offers high representational precision, it often suffers from poor surface quality and non-watertight geometry.**

- **Camp A — topology fidelity, watertightness sacrificed:** TRELLIS.2, Pixal3D (both O-Voxel-derived). Their READMEs *sell* open surfaces, non-manifold geometry and internal enclosed structures as features. Microsoft's own HF card then tells you to run hole-filling scripts "for applications requiring strictly watertight geometry (e.g., 3D printing)". Measured SSR: **17 % (TRELLIS.2)** and **7 % (Pixal3D)**.
- **Camp B — manufacturability prioritized:** Hi3D v1.0 / Twinkle3D (SPAR3D-family, ear-clip hole fill, largest-component retention), Direct3D-V3 ("implicit manifold regularization… to suppress non-watertight surfaces"), Direct3D-S2's optional `remesh` path.

Note the inversion in the Hi3D study: **TRELLIS.2 beats Hi3D on ULIP-2 (49.32 vs 48.07) and Uni3D (44.18 vs 42.14) — semantic/CLIP-space quality — and loses catastrophically on printability (17 % vs 90 %).** Any evaluation that stops at CLIP/ULIP metrics will rank these in exactly the wrong order for manufacturing.

### I.3 Other printability / watertightness measurements

- **Cyc3D** (arXiv **2608.28080**, 2026-08-28) — *"Evaluating Cyclic Structural Stability and Asset Usability in Image-to-3D Generation."* Decomposes Representation Quality into Geo. Struct., Ref-View Fid., **Mesh Qual. = Smoothness × Integrity**, **Mesh Effic.** (face-density distribution after quadric decimation to a common budget), and **UV Param. = Φ_uv(R_uv, R_eff, 1 − R_seam)**; plus a render→re-generate→re-align **view-cycle** protocol. Table 2 (verbatim): Hunyuan3D (closed) 82.6 / 70.2 / 83.9 / 89.1 / 68.8 / 83.7 / **47.1**; Tripo3D v3.1 (closed) 75.2 / 59.1 / 84.2 / 86.9 / 78.8 / 87.3 / **45.6**; Stable Zero123 45.3 / 34.5 / 41.6 / 51.5 / 70.0 / 54.9 / 25.5; Magic123 51.0 / 37.4 / 59.3 / 62.1 / 70.5 / 62.6 / 27.6; DreamCraft3D 63.1 / 42.4 / 33.8 / 75.2 / 69.5 / 72.1 / 27.8. Headline: *"even the strongest methods achieve cycle-stability scores below 48."* **Caveats: only 5 systems, and NONE of the 2025-26 feed-forward open models (TRELLIS, TRELLIS.2, Pixal3D, Step1X-3D, SUPRA-Tex, Direct3D-S2/V3) are evaluated. Cyc3D does not report a "% watertight" column — anyone quoting it as a watertightness percentage is misreading it.**
- **TopSDF** (2611.18708) — triangle **aspect ratio** as a concrete mesh-quality metric: 0.37 → 0.49, +0.86 dB PSNR on Mip-NeRF 360. The most printability-adjacent *metric* that actually moves.
- **MODL** (2611.25414) — "Watertight Mesh Optimization of Textured Objects": optimizes geometry *and* view-dependent appearance **directly on a watertight triangle mesh** (Laplacian-preconditioned vertex updates + curvature-adaptive remeshing). The closest thing to a "make it printable" pipeline in 2026.
- **MeshRepair** (2610.14113) — a repair *network* (prefix-LM, delete-then-add face edits) targeting "holes, stray faces, duplicated faces" in generated meshes; its defect statistics are the closest thing to a "% defective" figure for generated meshes.
- **Negative result:** arXiv queries for `all:"3D printing" AND all:"image-to-3D"`, `all:"printability" AND all:"mesh generation"`, and `all:"manifold" AND all:"mesh generation"` return **no 2026 benchmark reporting "% of generated meshes that are watertight / manifold / sliceable" across a model roster**. The Hi3D SSR table is effectively the only such measurement, and it covers 8 baselines at one slice.

**Net: the Hi3D SSR table is the single best printability instrument in the field, and it is author-run on a single slicer (Bambu Studio / PrusaSlicer CLI) with one profile, at one scale (100 mm longest AABB edge), with no pre-repair. Its absolute numbers should not be treated as portable, but the *ordering* (low-res models 97-100 %, 1024³ TRELLIS-family 7-17 %, Hi3D 1536³ 90 %) is consistent with the independent Topoheal census ordering (TRELLIS.2 100 % fail, TRELLIS 35 % fail, Hunyuan3D-2 0 % fail).**

### I.5 The licensing traps

- **Territory exclusion (Hunyuan 3.x):** output assets cannot be used in the EU, UK or South Korea. Nothing else in this landscape has a geographic restriction.
- **Non-commercial by default (MeshAnything):** S-Lab License 1.0 requires contacting the authors for commercial use.
- **De facto non-commercial (Shape-E):** MIT code, but OpenAI's model card says *"we advise against employing them for commercial purposes at this time."*
- **Revenue cliff (SF3D / Stability):** licenses terminate above $1 M annual revenue; registration and "Powered by Stability AI" attribution required.
- **Badge requirement (Hi3D):** "Powered by Hi3D 1.0" on any commercial integration embedding the model — but **standalone mesh outputs are exempt**, which makes Hi3D commercially usable for mesh production.
- **Partial non-commercial (SUPRA-Tex):** MIT completion weights but a Qwen-Research-licensed material adapter.
- **Training-on-outputs asymmetry:** Hunyuan forbids it (§5(b)); Hi3D explicitly permits it (§2.2); Stability forbids using outputs to improve a foundational generative model (IV.b).
- **No license at all:** Hunyuan3D-Buffalo 1.0 ships without a LICENSE file.
- **Public-domain-ish outlier:** TRELLIS, TRELLIS.2, Pixal3D, PartCrafter, Step1X-3D, 3DTopia-XL, Direct3D-S2/V3, TripoSR are MIT / Apache-2.0 with no MAU or revenue gate.

### I.6 CAD-downstream reality check

- **Nothing here is CAD.** The Topoheal census is blunt: *"It cannot do B-rep, so STEP, IGES and Parasolid are outside it entirely, and there is no tolerance check at all."* Every model surveyed outputs a triangle mesh (GLB/OBJ/PLY/STL at best — Tencent Cloud 3.1 Pro added **STL/USDZ/FBX** export, and Tripo supports FBX quad meshes). None produces a parametric/B-rep solid, feature tree, GD&T, or tolerances. All of them also **destroy absolute scale**: Hi3D explicitly normalizes to unit max radius, TRELLIS/Pixal3D emit unit-AABB meshes, and only Tripo's `auto_size` and Tripo's `v3/generation/*` promise real-world metres.
- **Triangle budget is a second, separate blocker.** The census's median generated asset is **77,402 faces** and 79.8 % of assets exceed Unity's 30 k mobile triangle cap. TRELLIS.2-4B's median is 290,881; TripoSG's is 1,367,152; Hi3DGen's is 632,684. For CAD/print you are almost always decimating by 10-100× after the fact, which changes the topology you were promised.
- **UV/PBR maturity is bimodal.** 2025-26 models either do **full PBR** (TRELLIS.2, Hunyuan3D-2.1, Pixal3D, 3DTopia-XL, SUPRA-Tex) or **nothing / geometry-only** (Hi3D, Direct3D-S2/V3, Hunyuan3D-Omni, Hunyuan3D-Part, MeshAnything). RGB-only sits in the middle (TRELLIS v1, Hunyuan3D-2.0, Step1X-3D, TripoSR, Shape-E). **Nothing between TRELLIS v1 (2024) and Hunyuan3D-2.1 (June 2025) shipped PBR** — that transition happened in one release.
