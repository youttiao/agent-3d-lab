# 技术路线全景

> 调研时间：2026-11-23
> 目的：回答两个问题——**现在别人做到了什么程度**，以及**我们该走哪条路**。

---

## 结论

**有五条路，我们该走其中两条半。**

| 路线 | 是干什么的 | 我们的用 | 判断 |
| --- | --- | --- | --- |
| **A. 代码参数化 CAD** | Agent 写 build123d Python，出 STEP | ✅ 主线 | **已在用，是地基** |
| **B. CAD → 机器人描述** | 从 CAD 模型自动生成 URDF/MJCF，自动推关节限位 | ✅ 主线 | **上游 0.11 刚补上，正是我们要的**。我们已跑通一轮，见 [`07`](07-CAD到URDF到MuJoCo.md) |
| **C. AI 生成网格** | 扩散模型出 mesh（TRELLIS / Hunyuan3D…） | ⛔ | 机械件用不上，Mac 也跑不动。**独立普查证实：好模型可切片率 90%，差的只有 7–17%** |
| **D. GUI 驱动（MCP）** | Agent 接管 Blender / FreeCAD 的 Python | 🟡 | 等真有"看着改"的需求再上 |
| **E. 仿真闭环** | MuJoCo / Isaac 里跑起来验 | ✅ | 本机已有 mujoco 4.0.1，**已接通** |

**"两条半"**：A + B + E。B 和 E 在上游新版里是连着的。

### ⚠️ 一条贯穿全文的方法论

调研和实操都指向同一件事：

> **「能跑」不等于「对」，而且检查器和引擎说的不是同一件事。**
>
> - 文本生成 CAD 的 SOTA：**代码执行成功率最低（2%），几何误差却最高（CD 220）、IoU 近零** ——
>   「它一贯生成可执行的代码，却没抓住几何规格」。
> - 我们自己的：`cad urdf validate` 报 `total mass 0.81 kg`，
>   MuJoCo 加载后只剩 **0.06 kg**，而且**一句警告都不打**。
>
> 结论：**凡是跨边界的检查，都得让目标系统真的跑一遍，把数字拿出来。**
> 这就是本仓库为什么有 [`checks/urdf_probe.py`](../checks/urdf_probe.py)
> 和 [`checks/joint_sweep.py`](../checks/joint_sweep.py)。


### 生态成熟度的一句话总结

> **3D + Agent 这块，没有"官方答案"。**
> Anthropic 官方 skills 仓库（`anthropics/skills`）里**一个 CAD / 3D skill 都没有**
> （只有文档、图像、办公类），代码搜索 `cad|step|stl|build123d|openscad` 零命中。
> 整个生态由社区扛着，其中 `earthtojake/text-to-cad` 一家 ★27k，
> 基本是事实标准。
>
> 这意味着：**跟着上游走比自己造轮子划算得多**，
> 但也意味着上游的改版会直接砸到你头上（我们这次就砸到了）。

### 但官方在**连接器**上入场了（更正一条）

> ⚠️ **更正**：说"官方完全没碰 3D"是不准确的。
> 2026-04-28 Anthropic 发了 **"Claude for Creative Work"**，
> 带来 **9 个 MCP 连接器**，其中跟 CAD 相关的是
> **Autodesk Fusion** 和 **Blender**（Blender 那个是 Blender 开发者自己做的，
> Anthropic 还成了 Blender Development Fund 的赞助方）。
>
> 但要说清楚它是**哪条路**：
> - 这些是 **chat 产品的连接器**，不是 Claude Code 的 skill / 插件；
> - 全部走开放 MCP，所以别的客户端也能用；
> - 全部**免费**，不分套餐。
>
> 对我们来说：**Claude Code 这条路上，官方没给 CAD 方案**，
> 走的还是社区的 text-to-cad。

## 路线 A：代码参数化 CAD（地基，已经在用）

### 是什么

Agent 写一段 Python，用 build123d（OpenCascade 的 Python DSL）描述几何，
跑起来产出 **STEP**（主格式），再导出 STL / 3MF / GLB / DXF。

不是"让 AI 画图"，是"**让 AI 写代码**"。所以：

- 产出是**参数化**的：改一个常量，模型重算
- 每个数都有出处（写在代码里，不是隐在网格里）
- 可以复算、可 diff、可 review

### 现在的状态

**我们本机已经齐了**（见 [`02-本机工具链.md`](02-本机工具链.md)）：

```
cadgen 0.6.5 · build123d 0.11.1 · OCP · playwright+chromium · ezdxf · numpy
```

已装 13 个 skill（`earthtojake/text-to-cad` 的 0.6.6 代），
已跑通一个完整案例（Robotiq 夹爪 V 型槽指尖逆向）。

### 上游已经走到哪（**重要**）

`earthtojake/text-to-cad` —— ★27,167 · 2,586 forks · MIT · **2026-11-23 当天还在推 commit**

上游在 0.6 之后做了**大改版**，现在是 **0.11.16**：

| | 0.6（我们装的） | 0.11（上游现在） |
| --- | --- | --- |
| 包 / 命令 | `cadgen` | `cad`（`cadgen` 保留为弃用别名） |
| skill | 13 个，按**文件格式**划分 | 8 个，按**产出**划分 |
| 架构 | 跑脚本 → 写文件 | **常驻引擎 + 文档模型 + 实时 viewer** |
| 建模 API | `@step(out=...)` 装饰器 | `@model` 装饰 + `cad model export` |
| 旧 skill 去哪了 | — | `urdf/srdf/sdf` → `robot-simulation`；`dfm/dfam-check` → `cad` 的可制造性检查；`gcode/bambu-labs` → `print3d`；`dxf` → `cad`；`step-parts` → 独立服务 |
| 新增 | — | **`fea`**（有限元）、**`pcb`**（KiCad）、`render` |
| MCP | 无 | `cad-mcp`（Claude Code 可直接接） |

新架构最大的变化是**"文档"这个概念**：

> 模型跑起来 → 引擎里存成一个文档 → **你打开的浏览器页面跟着实时更新**
> → 导出只是导航栏右边的"下载"按钮

还有 `model.param(...)`：**人在 viewer 里直接调一个数字，模型自动重算**。
这对"和朋友一起迭代设计"非常有用。

> 升级细节和风险见 [`05-升级到0.11.md`](05-升级到0.11.md)。

### 这条路的失败模式（要提前知道）

| 坑 | 说明 |
| --- | --- |
| `build123d` 的 `Box` 默认 `align=CENTER` | 几何中心在原点，不是 `MIN`。底面贴 Z=0 必须显式写 |
| 装饰器 `out=` 相对**脚本**，不相对 cwd | 换目录跑就写到别处 |
| `import` 里的 `bd` 属性 | 延迟导入，别在 import 时碰内核 |
| 尺寸对了形状错了 | **必须出图看**。尺寸对 ≠ 形状对 |
| 厂商件直接改 | 应该读进来（`step.read`）分析，再**参数化重建**，别直接改 STEP |

## 路线 A 续：失败模式排序（**最有用的部分**）

上面这些坑是"我们踩过的"。下面这些是**整个社区量化出来的**，按证据强度排序：

| # | 失败模式 | 说明 |
| --- | --- | --- |
| 1 | **摆放/对齐** | Agent 最大的失败类。把 `align=(0,0,0)` 这种数字元组当枚举传、把 `"center"` 当字符串传、猜原语的中心和轴。`agentcad` issue #197 记录了一次 GPT-5 Nano 跑 CADGenBench，**7 次以上栽在这**。社区为此加了 `bbox_point(shape, x='min', ...)`、`bbox_size(shape)` 这种"别猜"的辅助 API |
| 2 | **选择器语法幻觉**（CadQuery 侧） | 写出 `">Z and (not (circle or loop))"` 这种自己发明的选择器字符串 |
| 3 | **内核拒绝倒角/圆角** | B-rep 能倒圆角，也能**拒绝**倒。`ValueError: Failed creating a fillet with radius of 2.0` |
| 4 | **用了没定义的参数** | 模型够强之后最大的错误类。是 agent 的 bug，不是 CAD 语言的 |
| 5 | **静默的尺寸错误** | 代码跑通、几何合法、**设计是错的**。只有写死尺寸 `assert` 能抓 |

第 5 条最阴险，也最难防。对策（text-to-cad 的 `cad` skill 明写）：

```python
@model
def bracket():
    body = bracket_body(80, 6, 8)
    assert abs(body.bounding_box().size.X - 80) < 1e-6, body.bounding_box().size
    return body
```

> ⚠️ 关于"build123d 的 `align=CENTER` 默认是坑"这条：
> 我们自己的项目确实按 `align=(CENTER, CENTER, MIN)` 写，也确实避开了坑；
> 但**没有公开评测把它当作一条独立的失败模式**统计过。
> 有据可查的是上面第 1 条那个更宽的"摆放/对齐"类。
> 别把"align 默认居中"当成公开结论讲——它是我们项目里的好习惯。

### 一个更硬的对比数据

[grandpacad.com 的评测](https://grandpacad.com/blog/openscad-vs-cadquery-vs-build123d)
（19 个场景、同一 agent 框架、一次机会）：

| 模型 | OpenSCAD 失败 | build123d 失败 | 备注 |
| --- | --- | --- | --- |
| Gemini 3.5 Flash | 7 | 28/30 | build123d 错误里约 1/3 是幻觉 API 名，约 1/3 是内核拒绝 |
| Claude Opus 5.5 | 7 | 6 | 剩下的错误几乎全是"用了没定义的参数" |
| GPT-6.1 Sol | **0** | 2 | OpenSCAD 便宜 40%、快 26% |

两个关键结论：

1. **build123d 的错误 ≈ 一半是 API 用错**。
   往 skill 里塞一份**精确签名的 API 参考**，失败数从 28 掉到 22；
   再加一个"倒角失败就换小半径重试"的辅助函数，掉到 12–15。
   → **给 Agent 精确的 API 签名，比换模型管用。**
2. **模型档次决定成败**：强模型下 build123d ≈ OpenSCAD，
   弱模型下 OpenSCAD 赢一倍。
   → **便宜模型写不了 Python CAD**（社区原话：*"不是模型不会写 build123d，是便宜模型不会"*）。

### 第一个能量化比较的基准

**[CADGenBench](https://github.com/huggingface/cadgenbench)**（HuggingFace AI4Engineering，★157）：
两个任务（工程图→建模、现有 STEP→改）、**与工具无关**、
公开排行榜、提交只需一个 `output.step` + `meta.json`。

最有说服力的一条数据：**`pzfreo/build123d-mcp` 把同一个模型的分数从 0.360 提到 0.457，
CAD 合法率从 88% 提到 100%。**

> 这直接证明了一件事：
> **质量来自"工具中介的循环"（inspect → snapshot → fix），不是来自模型。**
> 这正是我们仓库里"每改一次必须出图看"那条规矩的理论依据。

## 路线 B：CAD → 机器人描述（**这条正是你要的**）

> "看数模之间的关系，把 URDF 里的一些关键值调整到合理的位置"

### 上游 `models/mujoco/` 样例项目就是干这个的

它的完整链路：

```
厂商原始 STEP
  → 读成模型
  → 把零件归组成 link（哪些打印件属于哪个连杆）
  → 从几何找关节轴
  → 声明材料（决定质量/惯量）
  → 导出 URDF
  → 用 MuJoCo function 生成 MJCF（碰撞体、执行器增益）
  → 跟 Menagerie 的模型 + 厂商自己的 URDF 对比
```

已经走通的真实机器人：

| 机器人 | 原始 CAD | 厂商描述 | Menagerie |
| --- | --- | --- | --- |
| SO-101 | `SO101 Assembly.step`（20 MB，97 个 occurrence） | `so101_new_calib.urdf` | `robotstudio_so101/so101.xml` |
| Trossen WidowX AI | `wxai_follower.step` | `wxai_follower.urdf` | `trossen_wxai/wxai_follower.xml` |
| UFACTORY xArm7 | `xArm 7 (XS1305).step` | `xarm_device.urdf.xacro` | `ufactory_xarm7/xarm7.xml` |
| Seeed reBot DevArm | `reBot_B601_RS_v1.0.step` | `ReBot_Arm_RS.urdf` | `seeed_rebot_devarm/seeed_rebot_devarm.xml` |
| ROBOTIS OP3 | `ROBOTIS-OP3_part_asm.stp` | `robotis_op3.urdf.xacro` | `robotis_op3/op3.xml` |

**`robotiq_2f85` 被明确列为候选**（"带连杆机构的小型知名夹爪：低风险"）。
我们手上恰好有 Robotiq 的零件。

### 关节限位可以自动推

`cad model ranges <id>` 的行为：

> 让每个关节**单独转**，直到它的子连杆**撞上父连杆**，打印每个止点（度或毫米）。

这正好是"把关键值调到合理位置"的一半。另一半是**执行器自身的行程**——
上游写得很清楚：

> 零件相撞那个止点，是几何的。
> **舵机自己的行程如果更窄，以数据手册为准。**

这就是 MicroDuck 的情况：`XL330` 的限位经减速比换算成 MJCF 里的
`range="-0.4363… 0.5236…"`（−25°/+30°），左右髋偏航是镜像的。

### 一条重要的"零位"约定

> **装配位就是每个关节的零位。** 关节限位 = 关节量程 − 装配时的角度：
> 一个指头在 0°~40° 量程里以 30° 装配，写出去就是 −30°~+10°，**不报警告**。
>
> 所以：**装配成什么位，就决定了描述文件里零位在哪**。
> 有控制器的，描述文件的零位应该对齐控制器的零位。

这解释了为什么"CAD 摆的姿势"本身就是一份设计决策。

### ⚠️ MicroDuck 走不了这条路（已核实）

上游明确写了为什么：

> Pollen Robotics 的 Microduck **做不到**：
> 它的 CAD 是一个需要账号才能导出的 Onshape 文档，
> 公开网格是 **CC BY-NC-SA**，
> 而 `microduck_rl` 里的 MJCF 是用 `onshape-to-robot` 从**同一个文档**生成的
> —— 所以**没有独立的、别人手写的参照物可以对比**。

**这条对我们很重要**：MicroDuck 的数模关系没法用"跟别人比"来验证，
只能靠**物理合理性自查**（舵机规格 ↔ 关节量程 ↔ 几何干涉三者自洽）。

## 路线 C：AI 生成网格（**对机械件不划算**）

### 现状

扩散模型路线（text-to-3D / image-to-3D）在 2026 年已经很成熟：
TRELLIS、Hunyuan3D、PartCrafter、SF3D、MeshAnything 等，输出纹理贴图和网格。
商业 API 有 Meshy、Tripo、Stability/Rodin、Sloyd 等。

### 但对我们要做的事，三个问题

1. **输出是"死"的网格**，没有参数、没有尺寸、没有装配关系。
   改一个孔径只能重新生成，不能"改个数字"。
2. **不保证流形/水密**，直接送去打印或转 STEP 会出各种问题。
3. **本机跑不了**：这堆模型要 NVIDIA GPU（8–24 GB 显存）。
   Mac 上只能走 API，**要钱**，而且还是拿不到参数化。

### ⚠️ 2026-11 更深一层的证据：问题比「死网格」严重得多

独立普查（2307 个真实资产、23 个生成器，同一引擎同一阈值）测出：

| | 数字 |
| --- | --- |
| 可切片率（好的 vs 差的） | **90%**（Hi3D 1536³）vs **17%**（TRELLIS.2）/ **7%**（Pixal3D） |
| 三角面中位数 | **77,402 面**；**79.8%** 超过 Unity 的 3 万面移动端上限 |
| 绝对尺度 | **基本都被毁掉**（Hi3D 归一化到单位最大半径；TRELLIS/Pixal3D 输出单位 AABB） |
| B-rep / 公差 | **一个都没有**（普查引擎明说「It cannot do B-rep, so STEP, IGES and Parasolid are outside it entirely, and there is no tolerance check at all」） |

**最扎人的一条**：TRELLIS.2 在语义指标（ULIP-2 49.32）上**赢** Hi3D（48.07），
在可切片率上却 17% vs 90%。
> **任何停在 CLIP/ULIP 指标上的评测，对制造场景会把排名排反。**

**要衡量就用「能不能切片 / 能不能装上」，别用「像不像」。**

还有一个普遍现象：**修复工具不是免费的** ——
普查实测修复过程引入了 **312 个新缺陷**，
> "A repair tool that reports no regressions has not looked for them."

### 判断

**机械件、支架、夹爪、URDF —— 一律不走这条路。**
AI 网格适合的是有机造型（角色、雕塑、概念件），
以及"先有个形再改"的快速草模。

> 📄 完整的输出侧技术档案（模型对照表、许可陷阱、可引用的普查数据、
> 以及 8 条「查不到 / 没验证」的明说）见
> [`08-AI生成3D的现状.md`](08-AI生成3D的现状.md)。

### ⚠️ 许可陷阱比技术问题更容易踩

| 模型 | 陷阱 |
| --- | --- |
| **Hunyuan 3.x** | **地域排除**：产出物不能用于**欧盟、英国、韩国** |
| **MeshAnything** | 默认**非商用**（商用要联系作者） |
| **Shape-E** | 代码 MIT，但 model card 明说建议不要商用 |
| **SF3D / Stability** | 年收入超 100 万美元即终止 + 需标注 |
| **Hunyuan3D-Buffalo 1.0** | 仓库**根本没有 LICENSE 文件** |

### 但有一座桥值得知道：网格 → 可编辑 CAD

如果你的输入**本来就是网格**（扫描件、外购件、别人给的 STL），
这条桥能把网格变回**参数化**模型：

| 项目 | 内容 |
| --- | --- |
| [`emirmrkaljevic/mesh2cad`](https://github.com/emirmrkaljevic/mesh2cad) ★137 · MIT | STL/OBJ/PLY → **可编辑 CAD**（STEP + 参数化的 CadQuery/OpenSCAD/FreeCAD），带图元拟合。同时有 CLI 和 MCP server |
| [`CADMAGEDDON`](https://github.com/kulibinai/cadmageddon) ★14 | 全本地的 mesh → CAD agent：中等尺寸开源 VLM（Qwen3.8-27B）驱动几何工具（实体识别、曲线/曲面拟合），单张 48 GB GPU 或当代笔记本可跑。**隐私动机**：专有零件不出本机。IoU 0.981 / GMS 0.909（CADENA 60 件子集） |
| [`bherbruck/solidcraft-cadbench`](https://github.com/bherbruck/solidcraft-cadbench) | 用本地模型跑 CADGenBench 的 MCP 管线，测 tok/s、首字延迟、合法率 |

> 我们的 Robotiq 案例其实就是这个思路的手工版：
> **读厂商 STEP → 量出尺寸 → 参数化重建**。
> 上游 `models/mujoco/` 把它做成了自动流水线。

#### ⚠️ mesh→CAD 这条桥，**确定性方法完胜学习方法**

真实机械件上的横评（CADENA-Bench，3396 个真实零件）：

| 系统 | IoU / GMS / IR | 说明 |
| --- | --- | --- |
| **mesh2cad**（确定性） | — | **6 个 Prusa 零件全部精确 STEP**，Hausdorff ≤ 0.22 mm，体积误差 ≤ 0.39%。弱在 0.2 mm 噪声下的圆角/沉头孔、球面、自由曲线 |
| CADFather（学习） | 0.909 / 0.721 / 0.0% | 最好，但弹簧 GMS 0.672、齿轮 0.660；每件 307 秒 |
| CADMAGEDDON（学习） | 0.981 / 0.909 | 曲面保真最好，**但没有具名参数**，圆角/倒角是显式实体 |

CADMAGEDDON 自己承认：
> "recovering design intent is beyond the current system."

→ **「mesh → 可编辑参数化机械 CAD」对简单基本特征已解决，对真实零件未解决。**


### 路线 C 补充：本地模型和数据集（2026 现状）

**没有成熟的专用开源 CAD 模型。**

### ⚠️ 安全：两个都必须知道的事

**1. 社区版 Blender MCP 的 `execute_blender_code` 无沙箱执行任意 Python**，
用你的用户权限、在活的 Blender 会话里。README 自己就写着
*"always save your work before using it"*。

好在**有 safe mode**：`BLENDER_MCP_SAFE_MODE=1`（**默认关**）会先校验脚本，
挡掉直接读写文件、拉起其他程序、联网、以及装持久化代码；
普通建模/材质/渲染/保存/导入导出照常，被挡的脚本会把**原因**返回给模型让它自己改。

**2. 官方 Blender Lab MCP 没有任何防护**，
官方自己警告：它执行 LLM 生成的代码，不防数据删除或外泄——
**用虚拟机，或用一台没有敏感数据的机器**。

**3. 端口撞车**：官方和社区版**默认都是 9876**。

FreeCAD 那边同类风险一样：`neka-nat/freecad-mcp` 的 `execute_code`
在 GUI 线程跑你的权限，**没有等价的安全模式**；
但它有个更安全的门 —— `execute_code_headless`（单独起 `freecadcmd` 进程）。

### 我们的选择：**`cad-mcp` 就够了**

上游 text-to-cad 自带 `cad-mcp`（`cad` 的别名包），装好就有，
Claude Code 插件会自动用上。**不用单独配 MCP server。**

### ⚠️ 反直觉：主流 CAD 厂商的 AI **都不能从自然语言生成零件**

| 厂商 | 2026 的 AI 实际能干什么 |
| --- | --- |
| **SolidWorks 2026** | 官方 AI 技能 12 个（Assembly Optimizer、Sketch Doctor、Hole Creator、Equations Assistant、Convert to Geometry…）。**没有一个能从自然语言生成零件** —— 全部作用于*已有*模型 |
| **Autodesk Fusion** | AI 功能是 Drawing Automation / AutoConstrain / **Generative Design**（后者是基于物理的拓扑优化，不是 AI 生成几何） |
| **Onshape AI Advisor** | 是**文档问答机器人**。官方 FAQ 明说 *"it does not generate designs, predict errors in real time, or make complex engineering decisions"*。Onshape 真正给 agent 的是 **FeatureScript MCP Server**（GA 2026-08-13），特点：FeatureScript 在 Onshape 原生执行，**保持完整参数关联性** |

> 这三家都没做「文本 → 零件」。**这条路（路线 A）目前没有厂商占住。**

### 判断

**现在不用装 Blender / FreeCAD。** 理由：

- 我们的活是机械件，代码参数化更快更准
- Blender 干不了参数化装配
- Agent 操作 GUI 的反馈环比"改代码→跑→出图"长
- 而 text-to-cad 的 `cad` **自带 MCP**，GUI 的必要性更低

**什么时候该上**：
需要处理有机曲面、需要做场景渲染、需要把实物照片变成网格，
或者要让人在 GUI 里手改模型（text-to-cad 没有这个，得靠社区的 Studio 类应用）。

## 路线 D 续：出图/渲染在 macOS 上怎么选（**本机已验证**）

Agent 要能"看见自己的作品"，就得能无头出图。macOS arm64 上的排序：

| # | 方案 | 本机实测 |
| --- | --- | --- |
| **1** | **OCCT 自带光栅器**（`cad step snapshot` / `cad model snapshot`） | ✅ **可用**，1600×1200 出图 **0.07～2 秒**，不用浏览器不用 GPU |
| 2 | Playwright + Chromium | ✅ 可用（0.6 时代用的就是这个），但要多下 150～300 MB 浏览器 |
| 3 | Blender 的 `bpy`（PyPI） | 有 `macosx_11_0_arm64` wheel，但**只支持 cp313**；`cad run` 里直接 `import bpy` 就能用 |
| 4 | `ocp-tessellate` + matplotlib | 最省事：纯 Python，无外部依赖 |
| 5 | `pyrender` | ❌ 2021 年后就没维护了，macOS 上没法用 |
| 6 | `pyvista`/VTK 离屏 | ❌ 走 OpenGL，macOS 没有 xvfb 等价物 |
| 7 | `trimesh.save_image()` | ❌ 要真实 OpenGL 上下文 |
| 8 | OpenSCAD 导 PNG | ❌ **macOS 无头最难受的一个**：要拉起 Qt/OpenGL 上下文 |

> 1、2 都是**本机实测过的**。3～8 是文档结论。

### 该做的工程习惯（数据支持，不是口号）

| 习惯 | 依据 |
| --- | --- |
| **每个模型写尺寸 `assert`** | 静默的尺寸错误是代码跑通时最难抓的一类，只有 assert 能抓 |
| **每改一次出一张图看** | CADGenBench 上"工具中介循环"让同一模型分数 0.360→0.457、合法率 88%→100% |
| **给 Agent 精确的 API 签名** | 社区评测里,塞进精确签名参考让 build123d 失败数从 28 掉到 22；加"倒角失败换小半径重试"掉到 12～15 |
| **内核对象只在函数体里读** | 0.11 的新契约：模块层读 `bd.Align` 会让脚本自己的进程也加载内核，每次 run 多 2～3 秒 |

### 不该做（现在）

- 装 Blender / FreeCAD / 切片器 —— 没需求，`cad` 自带 MCP
- 玩 AI 生成网格 —— 不出参数化
- 装一堆 MCP —— `cad-mcp` 一个先够用
- 用弱模型写 Python CAD —— 强模型下 build123d ≈ OpenSCAD，弱模型下 OpenSCAD 赢一倍

### 值得盯的

- **CADGenBench** —— 唯一能把"我的 agent 做的 CAD 好不好"变成数字的地方。
  想验证我们自己的工作流，就拿它当尺子。

- `models/tendon_hand/`（腱驱手 + 鲍登线）—— 跟 `dex-hand` 直接相关
